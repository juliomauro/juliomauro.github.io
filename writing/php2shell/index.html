PHP2Shell: 72 Hours of Internet-Wide Panic

Category: Security · Vulnerability Management · Incident Response
Level: Foundational

In late October 2026, two critical bugs in the PHP engine itself — not in any application, framework or plugin running on top of it — put an unknown but very large slice of the web on alert. The security community nicknamed the pair "PHP2Shell": CVE-2026-109618 and CVE-2026-109619, both scored 9.2 on CVSS v4.0, both unauthenticated, both remote code execution.

This isn't a writeup of a specific incident I worked. It's a look at the public chaos of those few days — the leaked disclosure, the scramble of advisories, the mitigation that only half-worked, and what the honeypot data actually showed once the dust settled a little.

Why This One Was Different

Most RCEs people deal with live in application code: a deserialization flaw in a library, a path traversal in an upload handler, a bad regex in an auth check. You can usually trace the bug to a decision someone made in a specific codebase.

PHP2Shell lives in session.upload_progress — a feature of the PHP engine itself, present since PHP 5.4. That means an application with genuinely clean code, properly validated input and no known vulnerable dependencies could still be exploitable, because the bug sits below all of that, in the runtime interpreting the request. Reporting at the time specifically called out e-commerce platforms like Magento, Shopware and WooCommerce as exposed regardless of their own code quality — because the flaw triggers before application logic ever runs, on some configurations.

Two Bugs, Two Different Memory Problems

CVE-2026-109618 is an out-of-memory corruption issue. When an OOM condition interrupts a vulnerable operation mid-flight, PHP can leave session data pointing at memory that has already been freed — and in some conditions, that can leak memory addresses, which is exactly what you need to defeat ASLR as a stepping stone toward full RCE.

CVE-2026-109619 is a different animal: a stale global state bug combining a fatal-error-backtrace use-after-free with OPcache type confusion. A later request handled by the same worker process can end up reusing memory that should have been freed, with a fatal-error-backtrace path that specifically applies to PHP 8.5.

Different root causes, different code paths — which turned out to matter a lot once people started patching.

Disclosed Early, Patched Fast

The details reportedly leaked on October 20, ahead of the coordinated disclosure date — which forced PHP to move the official release up from October 22. Fixed versions shipped October 21: 8.5.12, 8.4.27, 8.3.36, 8.2.35. Backports were reported for 8.1, 8.0 and 7.4, but anything older — including the long tail of PHP 5.x installs still quietly running somewhere — was left with no official fix at all.

That compressed timeline is exactly what turns a critical bug into a scramble: less time to coordinate messaging, less time to test patches at scale, and a disclosure that outran the people who were supposed to control its pace.

The Mitigation That Only Fixed Half the Problem

This is the part that made the following days genuinely chaotic for anyone trying to respond fast. The most widely circulated interim mitigation was setting session.upload_progress.enabled=0 in php.ini and restarting all workers.

That stopgap addresses CVE-2026-109619. It does not fully address CVE-2026-109618 — by some accounts, the advisory for 109618 doesn't even mention sessions as the trigger path. Two bugs sharing a nickname and a disclosure date, needing two different stopgaps, got flattened in a lot of first-pass guidance into "turn off upload_progress and you're covered." Teams that did exactly that and called it done were still carrying exposure from the other half of PHP2Shell.

This is a pattern worth internalizing on its own: when a vulnerability gets a catchy combined name, it's tempting to treat it as one fix. Read past the headline into the actual advisories before declaring victory.

The Industry Scramble

Within roughly 72 hours of disclosure, advisories and technical breakdowns went out from watchTowr, Imperva, Qualys, Arctic Wolf, Akamai, SOCRadar, Unit 42, JFrog, Bitdefender, Ellio and Upwind, among others — plus e-commerce-focused shops like sansec zeroing in on Magento/Shopware exposure specifically. That's not an unusual response to a critical CVE, but the volume and speed of it is a reasonable proxy for how seriously the industry took the "engine bug, not app bug" angle.

Public proof-of-concept repositories also appeared quickly on GitHub, which is its own double-edged part of this cycle: useful for defenders validating exposure, and a head start for anyone less well-intentioned.

What the Honeypots Actually Saw

PHP's own security team reportedly said, at release time, that no functional exploit was known to exist yet. That didn't hold for long. watchTowr's honeypot network reported real in-the-wild scanning activity, and one analysis clocked 33 distinct source addresses sending 743 requests carrying the session upload progress field by 23:00 UTC on the day activity picked up. Some of that traffic was tentatively linked by researchers to Potassium, a Mirai-derived botnet — though without confirmed evidence that payloads were actually downloaded or executed from those sessions.

The gap between "no known functional exploit" and "internet-wide opportunistic scanning within hours" is a useful reminder of what a CVSS 9.2 pre-auth RCE actually means in practice: you don't need a public working exploit for mass scanning to start. Automated probing for the vulnerable surface is cheap, and it starts the moment a CVE ID and a rough description exist.

The Actual Takeaways

  • Engine-level bugs break the "our code is fine" assumption. Clean application code is not a defense against a vulnerability in the runtime underneath it.
  • A combined nickname can hide two different fixes. PHP2Shell was two CVEs with two root causes and two separate stopgaps. Treat each advisory on its own terms, even when marketing (including security marketing) wants a single tidy name.
  • Patch, don't just mitigate. The interim config flags bought time; they were never a substitute for getting to a fixed PHP version, and for 5.x/7.x/8.0/8.1 installs, "getting to a fixed version" wasn't even an option without a platform upgrade.
  • Scanning starts before exploitation is proven. Honeypot data during this window is a good case study for why "no known exploit yet" is not a reason to deprioritize patching a 9.2.
  • A fifteen-year-old feature was the attack surface. session.upload_progress shipped in PHP 5.4. Old, boring, rarely-thought-about features are exactly where this kind of bug survives undisturbed for over a decade.

Sources: Sansec, Bitdefender, SOCRadar, Ellio, Upwind, watchTowr, Imperva, Qualys, Arctic Wolf, Akamai, Unit 42, JFrog. Verify CVE details against the official NVD/PHP advisories before acting on them operationally.

PHP2Shell: 72 Horas de Pânico na Internet

Categoria: Segurança · Gestão de Vulnerabilidades · Resposta a Incidentes
Nível: Fundamental

No final de outubro de 2026, dois bugs críticos no próprio motor do PHP — não em nenhuma aplicação, framework ou plugin rodando em cima dele — colocaram uma fatia desconhecida, mas muito grande, da web em alerta. A comunidade de segurança apelidou a dupla de "PHP2Shell": CVE-2026-109618 e CVE-2026-109619, ambas com nota 9.2 no CVSS v4.0, ambas não autenticadas, ambas de execução remota de código.

Isso não é o relato de um incidente específico que eu trabalhei. É um olhar sobre o caos público daqueles dias — o vazamento da divulgação, a corrida de advisories, a mitigação que só resolvia metade do problema, e o que os dados de honeypot realmente mostraram quando a poeira baixou um pouco.

Por Que Esse Caso Foi Diferente

A maioria dos RCEs que lidamos no dia a dia vive no código da aplicação: uma falha de deserialização numa biblioteca, um path traversal num upload handler, uma regex ruim numa checagem de autenticação. Geralmente dá pra rastrear o bug até uma decisão que alguém tomou num código específico.

O PHP2Shell vive no session.upload_progress — um recurso do próprio motor do PHP, presente desde o PHP 5.4. Isso significa que uma aplicação com código genuinamente limpo, input bem validado e nenhuma dependência vulnerável conhecida ainda assim poderia ser explorável, porque o bug está abaixo de tudo isso, no runtime que interpreta a requisição. As análises da época citaram especificamente plataformas de e-commerce como Magento, Shopware e WooCommerce como expostas independente da qualidade do próprio código — porque a falha dispara antes mesmo da lógica da aplicação rodar, em algumas configurações.

Dois Bugs, Dois Problemas de Memória Diferentes

CVE-2026-109618 é um problema de corrupção por falta de memória (out-of-memory). Quando uma condição de OOM interrompe uma operação vulnerável no meio do caminho, o PHP pode deixar dados de sessão apontando pra memória já liberada — e em certas condições, isso pode vazar endereços de memória, exatamente o que você precisa pra driblar o ASLR como passo intermediário rumo a um RCE completo.

CVE-2026-109619 é outro animal: um bug de estado global obsoleto combinando um use-after-free no backtrace de erro fatal com confusão de tipo no OPcache. Uma requisição posterior tratada pelo mesmo worker pode acabar reutilizando memória que deveria ter sido liberada, com um caminho de backtrace de erro fatal que se aplica especificamente ao PHP 8.5.

Causas raiz diferentes, caminhos de código diferentes — o que acabou importando muito quando as pessoas começaram a aplicar mitigações.

Divulgado Cedo, Corrigido Rápido

Os detalhes teriam vazado em 20 de outubro, antes da data coordenada de divulgação — o que forçou o PHP a antecipar o lançamento oficial, originalmente marcado pra 22 de outubro. As versões corrigidas saíram em 21 de outubro: 8.5.12, 8.4.27, 8.3.36, 8.2.35. Backports foram reportados para 8.1, 8.0 e 7.4, mas qualquer coisa mais antiga — incluindo a cauda longa de instalações PHP 5.x ainda rodando silenciosamente em algum lugar — ficou sem correção oficial nenhuma.

Esse cronograma comprimido é exatamente o que transforma um bug crítico numa correria: menos tempo pra coordenar a comunicação, menos tempo pra testar patches em escala, e uma divulgação que correu mais rápido do que quem deveria controlar o ritmo.

A Mitigação Que Só Resolvia Metade do Problema

Essa é a parte que tornou os dias seguintes genuinamente caóticos pra quem tentava responder rápido. A mitigação provisória mais divulgada foi setar session.upload_progress.enabled=0 no php.ini e reiniciar todos os workers.

Esse paliativo resolve a CVE-2026-109619. Ele não resolve totalmente a CVE-2026-109618 — segundo alguns relatos, o advisory da 109618 nem sequer menciona sessões como caminho de disparo. Duas falhas compartilhando um apelido e uma data de divulgação, precisando de dois paliativos diferentes, acabaram achatadas em muita orientação de primeira hora em "desliga o upload_progress e tá resolvido". Times que fizeram exatamente isso e deram o caso por encerrado continuavam carregando exposição da outra metade do PHP2Shell.

Esse é um padrão que vale internalizar por si só: quando uma vulnerabilidade ganha um nome chamativo combinado, é tentador tratá-la como uma correção só. Leia além da manchete, entre nos advisories de verdade antes de declarar vitória.

A Correria da Indústria

Em aproximadamente 72 horas após a divulgação, advisories e análises técnicas saíram da watchTowr, Imperva, Qualys, Arctic Wolf, Akamai, SOCRadar, Unit 42, JFrog, Bitdefender, Ellio e Upwind, entre outras — além de empresas focadas em e-commerce, como a sansec, mirando especificamente a exposição de Magento/Shopware. Isso não é uma resposta incomum pra um CVE crítico, mas o volume e a velocidade são um bom indicador de quão a sério a indústria levou o ângulo "bug no motor, não na aplicação".

Repositórios públicos de prova de conceito também apareceram rápido no GitHub, o que é parte do próprio ciclo de faca de dois gumes: útil pra quem defende validar exposição, e um atalho pra quem tem intenções menos boas.

O Que os Honeypots Realmente Viram

A própria equipe de segurança do PHP teria dito, no momento do lançamento, que nenhum exploit funcional era conhecido até então. Isso não durou muito. A rede de honeypots da watchTowr reportou atividade real de varredura no mundo real, e uma análise cravou 33 endereços de origem distintos enviando 743 requisições carregando o campo de progresso de upload de sessão até as 23h UTC do dia em que a atividade decolou. Parte desse tráfego foi tentativamente ligado por pesquisadores ao Potassium, um botnet derivado do Mirai — embora sem evidência confirmada de que payloads tenham realmente sido baixados ou executados a partir dessas sessões.

A distância entre "nenhum exploit funcional conhecido" e "varredura oportunista em escala de internet em questão de horas" é um lembrete útil do que um RCE pré-autenticação com CVSS 9.2 realmente significa na prática: você não precisa de um exploit público funcionando pra que a varredura em massa comece. Sondagem automatizada pela superfície vulnerável é barata, e começa no momento em que existe um ID de CVE e uma descrição mínima.

Os Aprendizados de Verdade

  • Bugs no nível do motor quebram a premissa de "nosso código tá limpo". Código de aplicação limpo não é defesa contra uma vulnerabilidade no runtime por baixo dele.
  • Um apelido combinado pode esconder duas correções diferentes. O PHP2Shell eram duas CVEs com duas causas raiz e dois paliativos separados. Trate cada advisory nos próprios termos, mesmo quando o marketing (inclusive o de segurança) quer um nome único e arrumadinho.
  • Corrija, não só mitigue. As flags de configuração provisórias compraram tempo; nunca foram substituto de chegar numa versão corrigida do PHP, e pra instalações 5.x/7.x/8.0/8.1, "chegar numa versão corrigida" nem era opção sem um upgrade de plataforma.
  • A varredura começa antes da exploração ser comprovada. Os dados de honeypot nessa janela são um bom estudo de caso de por que "nenhum exploit conhecido ainda" não é motivo pra despriorizar o patch de um 9.2.
  • Um recurso de quinze anos foi a superfície de ataque. O session.upload_progress foi lançado no PHP 5.4. Recursos antigos, chatos e raramente lembrados são exatamente onde esse tipo de bug sobrevive intocado por mais de uma década.

Fontes: Sansec, Bitdefender, SOCRadar, Ellio, Upwind, watchTowr, Imperva, Qualys, Arctic Wolf, Akamai, Unit 42, JFrog. Confira os detalhes das CVEs no NVD/advisories oficiais do PHP antes de agir operacionalmente com base neles.
